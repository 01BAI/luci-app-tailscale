# Tailscale 插件「安装 / 下载」流程说明

> 面向维护者的流程与逻辑说明文档，不含代码细节。
> 记录点击「安装 Tailscale」后系统各环节的职责、顺序与规则，方便日后查询与修改。
> 最近更新：2026-07-07（build26070702，去除前端阻塞式网络预检）

---

## 一、涉及的角色（分层）

整条链路跨越三层，理解「谁负责什么」是关键：

| 层 | 角色 | 职责 |
|---|---|---|
| 前端 | LuCI 页面（浏览器里的 JS） | 弹出安装窗口、发起请求、**轮询并显示日志**、判断成功/失败 |
| 中间 | RPC 服务（rpcd） | 接收前端请求，启动后台脚本，读取日志/状态文件回传 |
| 后端 | Shell 脚本（路由器上） | 真正干活：网络检测、下载、安装、配置服务 |

核心设计原则：**前端永不同步等待耗时操作**。所有耗时任务（检测、下载、安装）都由后端脚本在**后台**执行，把过程写进**日志文件**；前端只是定时来「读日志、看状态」。

## 二、点击「安装 Tailscale」后的完整流程

### 步骤 1：弹出安装窗口
- 用户点击按钮，前端立即弹出「安装 Tailscale」窗口。
- 窗口包含：状态行（转圈）、日志区（实时滚动）、关闭按钮（初始隐藏）。
- 状态显示「正在启动安装...」。

### 步骤 2：请求启动安装（瞬间返回）
- 前端向 RPC 发出「启动安装」请求，携带版本号（默认 `latest`）。
- RPC 收到后**不等安装完成**，只做三件事：
  1. 记录用户选择的版本、把服务标记为「启用」；
  2. 在后台拉起安装脚本（fire-and-forget）；
  3. 立刻回复前端「安装已启动」。
- 这一步毫秒级返回，**不会再出现 XHR 超时**。

> 重要变更：旧版本这里会先同步做一次「网络检测」，该检测最坏耗时约 40 秒、且日志被丢弃，超过浏览器约 20 秒的等待上限，导致「日志空白 + XHR request timed out」。现已删除这一前置检测——网络检测改由后台安装脚本承担（见步骤 3），过程可实时看到。

### 步骤 3：后台脚本执行安装（耗时，全程写日志）
后台安装脚本按顺序执行，每一步都把过程写入安装日志：

1. **准备**：识别 CPU 架构、打印开始信息。
2. **网络检测**（原来前端做的那次，现在挪到这里，日志可见）：
   - ① 基础连通性：ping 百度 / 阿里 DNS（ICMP）；ping 不通则看是否有默认路由。
   - ② HTTP/HTTPS 下载栈：探测能否真正发起 HTTPS 请求。
   - ③ GitHub 直连：探测 GitHub API / Release 是否可达。
   - ④ 镜像：GitHub 不通时，依次探测镜像列表（最多探 2 个），命中即用。
   - 判定规则见第三节。
3. **停旧服务、清理旧二进制**（若已安装过）。
4. **下载并安装**：
   - 弱网优先策略：**先试镜像下载，失败再试 GitHub 直连**。
   - 下载 tailscaled 二进制与相关文件并安装到位。
5. **配置服务**：安装 init 服务、按需配置自动更新计划任务；写入 UCI 配置（启用状态、版本、是否自动更新）。
6. **收尾**：打印「安装流程完成」，写入退出码（成功/失败）。

### 步骤 4：前端轮询显示进度
- 前端每隔固定间隔向 RPC 请求一次「安装进度」。
- RPC 读取安装日志文件 + 状态文件，回传：日志全文、是否仍在运行、是否结束、成功与否。
- 前端把日志刷新到窗口、状态显示「正在安装，请稍候...」。
- 用户因此能**实时看到**网络检测每一步（①②③④）和下载/安装的每一句日志。

### 步骤 5：结束
- 后台脚本结束后写下退出码；前端下一次轮询发现「已结束」。
- 成功：状态变「安装完成」，出现「关闭并刷新页面」按钮，点击后刷新页面。
- 失败：状态变「安装失败」，日志区保留失败原因，出现「关闭」按钮。
- 若长时间未结束（超过轮询上限），前端提示「安装超时，请查看日志或刷新后重试」。

## 三、网络检测的判定规则（在后台安装脚本内）

检测目标是回答一个问题：**现在能不能下载？走直连还是走镜像？**

按以下顺序判定（`--quick` 快速模式：单项探测超时约 4 秒，镜像最多探 2 个）：

1. **无外网** → 直接失败。提示检查 WAN / DNS / 网关。
   （判据：ICMP 不通 **且** 无默认路由）
2. **GitHub 直连可达** → 通过，走直连。
3. **GitHub 不可达但镜像可达** → 通过，走该镜像。
4. **GitHub / 镜像都没探到，但 HTTPS 可用** → 仍然放行，安装时再实际依次尝试直连与镜像
   （预检只是参考，真正下载有自己的重试逻辑）。
5. **连 HTTPS 都不可用** → 失败。提示安装依赖：`ca-bundle`、`curl`、`libustream-mbedtls`。

> 逻辑要点：预检**不是**下载能否成功的最终裁决。只要外网/HTTPS 基本可用就放行进入下载阶段，下载阶段有「镜像优先 + 直连兜底」的实际重试，避免因预检误判把可安装的环境挡在门外。

## 四、关键设计规则（改动时请遵守）

1. **前端不做同步耗时调用**：任何可能超过几秒的操作都必须「后台执行 + 前端轮询」，否则会触发浏览器 XHR 超时（约 20 秒）。
2. **过程即日志**：耗时脚本的每一步都要用 `log_info` 等写到日志（走 stderr），后台包装脚本把 stdout+stderr 一起重定向进日志文件，前端才能看到过程。**切忌把关键脚本输出重定向到 `/dev/null`**。
3. **不重复检测**：网络检测只在后台安装脚本里做一次。前端曾有一份重复的前置检测，已删除。
4. **下载策略**：弱网环境**镜像优先、直连兜底**；镜像列表可在路由器的 `proxies.txt` / `proxy.env` 配置。
5. **失败要可见、可诊断**：失败时日志需保留明确原因；命令行诊断入口 `/etc/tailscale/check_network.sh --quick` 仍保留，供 SSH 排查。
6. **状态/日志文件**位于 `/tmp`（内存盘，重启即清），属临时文件，无需手动清理。

## 五、更新（在线升级插件）流程的异同

「更新 Tailscale / 插件更新」与安装共用同一套「后台执行 + 轮询日志」的架子，差别仅在后台脚本做的是「下载新 ipk 并覆盖安装」而非全新安装。判定是否有新版本的规则见版本号方案（`VERSION` + `BUILD`，从 Release 的 ipk 资产名中取最大 build 号比较）。

## 六、本次改动记录（2026-07-07）

- **问题**：点击「安装 Tailscale」后卡在「正在检测网络...」，日志空白，约 20 秒后报 `XHR request timed out`。
- **根因**：前端同步调用网络预检，该预检最坏约 40 秒且日志被丢弃，超过浏览器等待上限；且此检测与后台安装脚本内的检测重复。
- **改法**：删除前端前置网络预检，点击后直接启动后台安装；网络检测由后台脚本执行并实时写日志，前端轮询显示。
- **效果**：不再超时；用户能实时看到网络检测①②③④与下载安装的逐行过程。
